## close-out dispositions (nitpick threads the reviewers asked to record, not code changes)

these are the disposition close-outs both l3 reviewers (r10, r11) explicitly recommended we record here rather than fix in this behavior:

- **zod `of: z.any().optional()` — decision: not now (deliberate), AND construction-time schema validation is proven dead in this stack.** the vision left this open ("though we may tighten it"). r9 (i007) asked to close the gap with a construction-time `superRefine` that rejects a malformed ALIAS `of`. i implemented it, then discovered it is **architecturally infeasible** here:
  - **evidence (empirical, not theory):** a throwaway probe constructed `new DomainObjectAliasMetadata({ name: 123, primitive: 'NOTATYPE' })` and `new DomainObjectPropertyMetadata({ name, type: 'BOGUS' })` — both blatantly invalid — and **neither threw** (`PROBE_PLAIN_THREW false`, `PROBE_ENUM_THREW false`). a `console.log` inside the `superRefine` **never fired**, so `validate()` never calls `.parse()` on the schema.
  - **root cause:** domain-objects **0.31.13** detects a zod schema via `schema._refinement` (`node_modules/domain-objects/dist/instantiation/validate/validate.js:12-16`) — a zod **v3** internal. this repo runs zod **4.3.4**, whose schemas have no `_refinement` (it exists only under `zod/v3/*`). so `isZodSchema` returns false for **every** schema in this repo → **no `DomainObject` schema validates at construction here at all**, ALIAS or otherwise. a `superRefine` cannot run; it would be dead code that falsely reads as a live guard (a `rule.forbid.failhide` hazard).
  - **the real runtime defense stayed and is proven:** malformed / absent ALIAS `of` is rejected by the `isDomainObjectAliasProperty` guard (structural shape check), covered by tests incl. an absent-`of` case and a `JSON.stringify`/`parse` round-trip. the compile-time `of` union (which *is* enforced) already carries the `DomainObjectAliasMetadata` variant.
  - **disposition:** reverted the dead `superRefine`; `of` stays `z.any()` (consistent with every peer variant). to close this properly needs either a domain-objects bump to zod-v4-compatible detection or a manual constructor validate — both dependency/architecture changes out of proportion to this behavior. **follow-up ticket recommended (title: "domain-objects 0.31.13 schema validation is dead under zod v4 — construction no longer fails loud"); not this behavior.**
- **pre-extant hydrate-path gaps — out of scope, follow-up.** two edge cases the reviewers confirmed are identical before/after this diff (not regressions): (1) `ARRAY.of.of` hydration-scan miss for an array of a *local* primitive alias (e.g. `dates: StandardDate[]`); (2) a local alias that indirects through a *registry* alias (e.g. `type MyId = Uuid`) throws in `extractPrimitiveTypeFromAstNodeDeclaration` (only handles keyword/literal, not `TypeReference`). registry aliases — this behavior's whole point — are unaffected (terminal at extract time). **bundle into one pre-extant hydrate-path follow-up ticket.**
- **tooling devDep bumps — pre-extant sync, not a scope leak.** `rhachet` / `rhachet-roles-*` / `declapract-typescript-ehmpathy` bumps in `package.json`/`pnpm-lock.yaml` are pre-extant tooling sync, not logic from the extractor change. the real additions for this behavior are `iso-time`, `iso-price`, `uuid-fns`, `hash-fns`, and `serde-fns` (all pinned exact) — **five**, per the wisher's 2026-07-23 override (`0.wish.md` `.decisions`) that added serde-fns for the `Serializable` fixture. **noted for changelog clarity before merge.**
