# vision: support template literal types as string

## the outcome world

### day-in-the-life

a developer models a domain object whose version field is a template literal type:

```ts
export interface SeaTurtleTag {
  /**
   * a semver-shaped tag, e.g. "v1.2.3"
   */
  version: `v${number}.${number}.${number}`;
}
```

they run domain object metadata extraction (e.g. to generate a schema). today it explodes:

```
UnexpectedCodePathError: could not extract property definition from interface member declaration
{ "propertyName": "version", "primaryTypeKind": 203 }
```

after this wish, it just works — `version` extracts as a `STRING` property, with `nullable` and `required` preserved exactly as declared.

### before / after contrast

| | before | after |
|---|--------|-------|
| `version: \`v${number}\`` | 💥 `UnexpectedCodePathError` (kind 203) | ✅ `STRING`, required, not nullable |
| `version: \`v${number}\` \| null` | 💥 throws | ✅ `STRING`, required, nullable |
| `version?: \`v${number}\`` | 💥 throws | ✅ `STRING`, optional, not nullable |

### the "aha" moment

the value clicks the moment a developer realizes they don't have to choose between **expressive types** and **extractable types**. they can keep the precise template literal type in their domain model (great for compile-time safety) and still get clean schema generation (template literals are just strings at runtime). no workaround, no widening their type to `string` just to appease the extractor.

## user experience

### usecases & goals

- **goal**: model a string with a constrained shape (semver, slug, prefixed id, formatted code) using a template literal type, and still generate runtime schemas from it.
- **who**: developers using `domain-objects-metadata` to extract schemas from interfaces that already use template literal types.

### contract inputs & outputs

the contract is unchanged in shape — only its domain of acceptance widens.

**input**: a TypeScript interface member whose type is a `TemplateLiteralType` (`SyntaxKind` 203), optionally unioned with `null`, optionally with a `?` optional token.

**output**: a `DomainObjectPropertyMetadata` with:
- `type: DomainObjectPropertyType.STRING`
- `nullable`: true iff `| null` present
- `required`: false iff `?` optional token present

### what it looks like to leverage

```ts
const properties = extractPropertiesFromInterfaceDeclaration(interfaceDeclaration);

expect(properties.version).toMatchObject({
  type: DomainObjectPropertyType.STRING,
  nullable: false,
  required: true,
});
```

identical to how a plain `version: string` is consumed today — that's the point.

### timeline

instant. extraction is a synchronous, single-pass AST walk. no new steps, no new flags. extant callers get the new behavior for free on upgrade.

## mental model

### how a user describes it to a friend

> "template literal types are just fancy strings, so the metadata extractor now treats them as strings — like it always should have."

### analogies / metaphors

same family as the prior fix for string-literal unions (`'a' | 'b' | 'c'` → `STRING`). a template literal type is "a string with a known shape." we already collapse literal unions down to their base primitive; this collapses template literals down to their base primitive (`string`) too.

### terms: theirs vs ours

| user term | our term |
|-----------|----------|
| "template literal type" | `TemplateLiteralType` / `SyntaxKind` 203 |
| "treat as a string" | `DomainObjectPropertyType.STRING` |
| "optional field" | `required: false` (from `questionToken`) |
| "can be null" | `nullable: true` (from `\| null` union) |

## evaluation

### how well it solves the goal

fully. the wish asks for template-literal props to extract as `string` with nullable/required preserved. the fix sits in `extractPrimitiveTypeFromAstNodeDeclaration` — the same "root primitive" transformer that already maps `StringKeyword → STRING`. adding `TemplateLiteralType → STRING` there means:

- **required, non-null** template literal → flows directly through `extractPropertyDefinitionFromAstNode`'s primitive check.
- **nullable** template literal (`\`...\` | null`) → in `extractPrimaryTypeFromMemberDeclaration`, the union has two subtypes (template literal + null). the template literal is **not** a `LiteralType`, so the homogeneous-literal-union path is skipped; it falls to the "two subtypes, one is null" branch, which returns the template literal node as the primary type with `nullable: true`. that node then resolves to `STRING`. ✅
- **optional** (`?`) → handled independently by the `questionToken` check, orthogonal to type. ✅

one small transformer change covers all three cases.

### pros

- minimal, surgical change — single transformer, mirrors extant `StringKeyword` handling.
- no contract surface change; purely widens acceptance.
- consistent with the prior precedent (string-literal-union fix).
- runtime-accurate: template literals *are* strings at runtime.

### cons / tradeoffs

- we discard the shape constraint (`v${number}...`) and collapse to `STRING`. the generated schema won't enforce the template pattern. this is acceptable and consistent — we already collapse `'active' | 'completed'` unions to `STRING` without preserving the allowed-values constraint.

### edgecases & pit of success

| edgecase | behavior |
|----------|----------|
| required template literal | `STRING`, required, not nullable |
| `\| null` template literal | `STRING`, required, nullable |
| `?` optional template literal | `STRING`, optional, not nullable |
| `array of template literals` (`\`v${number}\`[]`) | flows through array handler → `ARRAY of STRING` (template literal element resolves to STRING) |
| template literal unioned with another non-null type (`\`v${number}\` \| number`) | still throws `BadRequestError` — one primary type only, consistent with the extant rule |

the pit of success: the user keeps their precise type and gets correct extraction; the only "lossy" behavior (shape→STRING) matches what they already expect from literal unions.

## open questions & assumptions

### assumptions

- collapse of the template-literal shape to `STRING` (rather than preserve the pattern) is the desired behavior. **the wish explicitly states this** ("treat them as `string`"), so this is confirmed, not assumed.
- the fix belongs in `extractPrimitiveTypeFromAstNodeDeclaration` (root-primitive transformer), not deeper in the union logic. verified by trace of the nullable path above.

### questions (triaged)

each open question is marked `[answered]` (resolved now), `[research]` (defer to research phase), or `[wisher]` (needs wisher input).

1. **should the template shape (`v${number}...`) be preserved as a pattern/regex instead of collapsed to STRING?** — `[answered]` the wish says "treat them as `string`"; also consistent with the extant literal-union→STRING collapse. STRING it is.
2. **does the nullable case need new union-logic code, or does it fall out of the extant flow?** — `[answered]` falls out of the extant two-subtype branch (traced: a 203 node is not a 201 `LiteralType`, so it skips the homogeneous path). no new union code.
3. **must the fix reference the `SyntaxKind.TemplateLiteralType` enum rather than the literal `203`?** — `[answered]` yes. `SyntaxKind` numeric values are not stable across TS versions; the extant transformer always uses the enum (`extractPrimitiveTypeFromAstNodeDeclaration.ts:17-25`). execution must use the enum, never `203`.
4. **must the test asset use an *interpolated* template (`` `v${number}` ``) to actually produce kind 203?** — `[answered]` yes. a non-interpolated backtick type (`` `hello` ``) is a `NoSubstitutionTemplateLiteral` (kind 15) wrapped in a `LiteralType`, a different out-of-scope path. the asset must interpolate; the wish's own example already does.
5. **are array-of-template-literal and mixed-union (`template | otherType`) cases in scope as required acceptance?** — `[answered]` no. both are emergent consequences of the core fix (verified by trace), documented as illustrative edgecases, not mandatory deliverables. required acceptance stays: required + nullable + optional.

- no `[research]` items: no external dependency remains unverified (see groundwork).
- no `[wisher]` items: the wish + issue #21 fully specify behavior and acceptance.

## groundwork

### external research

- **TypeScript `SyntaxKind` 203**: verified against `node_modules/typescript/lib/typescript.d.ts:4377` — `TemplateLiteralType = 203`. installed TS version is `5.4.5` (`node_modules/typescript/package.json:5`). this confirms the `primaryTypeKind: 203` in the error message is indeed a template literal type. ✅
- no other external APIs/services referenced.

### internal research

- **error origin**: `src/domain.operations/extract/extractPropertyDefinitionFromAstNode.ts:175` throws `UnexpectedCodePathError('could not extract property definition...')` when no handler matches `primaryType.kind`. this is the exact error in the wish.
- **primitive transformer**: `src/domain.operations/extract/extractPrimitiveTypeFromAstNodeDeclaration.ts:17-22` maps `StringKeyword`/`NumberKeyword`/`BooleanKeyword` → primitives. natural home for `TemplateLiteralType → STRING`.
- **nullable union path**: `src/domain.operations/extract/extractPrimaryTypeFromMemberDeclaration.ts:54-96` — verified that a template literal in a `| null` union is *not* a `LiteralType`, so it correctly falls to the "two subtypes, one null" branch (line 86) and returns the template literal node with `nullable: true`.
- **test contract & vocab**: `src/domain.operations/extract/extractPropertiesFromInterfaceDeclaration.test.ts:202-268` — the `ClaimSearch` literal-union test is the precedent pattern: an interface test asset (`src/domain.operations/.test.assets/ClaimSearch.ts`) + `toMatchObject` assertions + `toMatchSnapshot`. our acceptance test should mirror this.
- **test asset pattern**: `src/domain.operations/.test.assets/*.ts` — each is a documented interface (e.g. `ClaimSearch.ts`, `MixedLiteralUnion.ts`). we'll add one with a template-literal prop covering required + nullable + optional.
- **precedent commit**: `00c9c64` "fix(extract): support string literal unions as primitive types (#17)" — the direct sibling fix; our change follows the same structure and scope.

## what is awkward?

- **shape loss feels slightly lossy.** `\`v${number}.${number}.${number}\`` carries real intent (semver shape) that we throw away by mapping to `STRING`. it's the right call (runtime-accurate, consistent with literal-union handling) but worth noting we're not capturing the constraint. a future enhancement could emit a regex/pattern alongside the `STRING` type — out of scope for this wish.
- **the union nullable path is implicit.** the fact that "template literal in a null union falls through to the generic two-subtype branch" works correctly but isn't obvious from reading the code; it relies on a template literal *not* being a `LiteralType`. the acceptance test for the nullable case is what locks this behavior in, so it must be explicit.
