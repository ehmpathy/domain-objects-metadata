# vision: regression coverage for string-literal unions

before painting the dream, the groundwork surfaced a load-bearing fact:

> **the acceptance criteria is already met by committed code (#17, v0.7.7).**

- ✅ test asset with a string-literal-union prop is present → `src/domain.operations/.test.assets/ClaimSearch.ts`
- ✅ unit test asserts it extracts as `string`, nullable/required preserved → `extractPropertiesFromInterfaceDeclaration.test.ts` (the `'should be able to extract properties from an interface with string literal unions'` case, plus a `MixedLiteralUnion` throw case)
- ✅ all 9 tests in that file pass today (`rhx git.repo.test --what unit --scope path://extractPropertiesFromInterfaceDeclaration --mode apply` → 9 passed)

so the "happy path" of this wish is **done**. the remaining value is in the genuine gap the groundwork found (see below), not in re-adding what is already present.

## the outcome world

### day-in-the-life

a maintainer refactors the extract pipeline (e.g. touches union-unwrap logic in `extractPrimaryTypeFromMemberDeclaration.ts`). they run the suite. if their change silently regresses `'active' | 'completed' | 'expired'` back to "unhandled union → throw" or "wrong type", a red test names the exact behavior that broke — at **both** the unit grain (property extraction) and the integration grain (full metadata for a domain object).

### before / after contrast

| | before this wish | after this wish |
|---|---|---|
| unit coverage of literal unions | ✅ present (#17) | ✅ unchanged |
| integration coverage of literal unions | ❌ absent — `extractDomainObjectMetadataForDeclarationInFile.test.ts` only exercises `Address`, `LoadingDock`, `Item` | ✅ a literal-union asset flows through the full pipeline a consumer actually uses |

### the "aha" moment

the value clicks when you realize `extractPropertiesFromInterfaceDeclaration` is not invoked in isolation by the broader pipeline — the nearest orchestrator grain above it, `extractDomainObjectMetadataForDeclarationInFile` (interface + class declaration → full `DomainObjectMetadata`), wraps it. the unit test guards the inner transformer; no test guards the literal-union behavior through that orchestrator grain. that's the silent-break surface still exposed. (note: i did not trace the full call graph above that orchestrator, so it is "the nearest untested orchestrator grain," not asserted as *the* sole consumer entry point.)

## user experience

- **usecase**: a maintainer evolves the extract logic and needs a safety net that the `'a' | 'b' | 'c'` → `STRING` behavior cannot silently regress.
- **contract inputs**: a `.test.assets/*.ts` fixture exposing a string-literal-union property (required, nullable, single-literal, plus number/boolean literal unions and an array-of-literal-union for completeness) — and, for the integration grain, a domain-object **class** declaration (e.g. `extends DomainEntity<...>`), since `extractDomainObjectMetadataForDeclarationInFile` keys off `isClassDeclaration`.
- **contract outputs**: extracted property metadata where literal-union props carry `{ type: STRING|NUMBER|BOOLEAN, nullable, required }`, asserted explicitly **and** snapshotted (per the repo's snapshot+assertion convention).
- **what leverage looks like** (a new case added to the present `extractDomainObjectMetadataForDeclarationInFile.test.ts` — see note below on file convention):
  ```ts
  const metadata = extractDomainObjectMetadataForDeclarationInFile({ file, classDeclaration });
  expect(metadata.properties.status).toMatchObject({
    type: DomainObjectPropertyType.STRING, nullable: false, required: true,
  });
  expect(metadata).toMatchSnapshot();
  ```
- **file-convention note**: this repo has **zero** `.integration.test.ts` files; orchestrator tests that read assets from disk live as plain `.test.ts` and run under `--what unit`. so "integration coverage" here = a new case in the orchestrator-level `.test.ts`, **not** a separate `.integration.test.ts`. the unit-vs-integration distinction is real by *grain of operation* (transformer vs orchestrator), not by *file name*.
- **timeline**: write/extend asset → add the integration test case → `--mode apply` to greenlight + snapshot → done. (additive test code, no production change — low effort, though a class-backed asset may surface decoration requirements like `unique`/`primary`.)

## evaluation

### how well it solves the goal
- the stated acceptance ("a test asset is present; a unit/**integration** test asserts string + nullable/required") is the literal goal. unit is satisfied; the word **integration** is the unmet half. closing it fully discharges the wish rather than rubber-stamping it.

### pros
- closes a real silent-break surface (end-to-end path consumers use).
- cheap, deterministic, no external deps.
- snapshot gives reviewers a visual diff of the extracted shape.

### cons / cost
- low risk of asset sprawl if we add a brand-new fixture instead of extending one.
- snapshot churn if the metadata shape legitimately evolves (acceptable — that's the signal working).

### edgecases the asset should pin (already pinned at unit grain; mirror at integration grain as needed)
- required literal union → `STRING`, `nullable: false`
- nullable literal union (`... | null`) → `STRING`, `nullable: true`
- single literal (`'search'`) → `STRING`
- number literal union (`1 | 2 | 3`) → `NUMBER`
- boolean literal (`true | false`) → `BOOLEAN`
- array of literal union → `ARRAY` of `STRING`
- mixed union (`'active' | 1`) → throws `BadRequestError` (negative-path guard)

pit-of-success: assets are declarative `.ts` interfaces; the test compiles them via a real `ts.createProgram`, so they can't drift from how the library actually parses source.

## open questions & assumptions

each question is triaged: **[answered]** (resolved now via logic/code), **[research]** (defer to research phase), **[wisher]** (only the wisher can decide).

1. **[wisher] scope of "lock in"**: unit coverage is already present. is the intent (a) confirm + stop, or (b) add the absent orchestrator-grain coverage at `extractDomainObjectMetadataForDeclarationInFile`? this vision recommends **(b)** — the only reading where the wish produces new value and honors "integration" in the acceptance. but (a) is legitimate and only the wisher can pick. **this is the one true blocker for execution scope.**

2. **[wisher] asset strategy** (contingent on #1 = b): three viable paths, all technically sound — (i) extend a current class-backed asset with a literal-union prop; (ii) promote `ClaimSearch` to a domain-object class (add `export class ClaimSearch extends DomainEntity<...> implements ClaimSearch {}`); (iii) add a new dedicated class asset. recommendation: **(ii)** — reuses the already-purpose-built literal-union fixture with one added class line, lowest churn. final call is wisher preference, but any of the three works; execution can proceed on the recommendation if the wisher stays silent.

3. **[answered] where does the test live?**: not a separate `.integration.test.ts` — the repo has zero of those; a new case goes in `extractDomainObjectMetadataForDeclarationInFile.test.ts` (orchestrator-level `.test.ts`, run under `--what unit`). verified via glob over `src/**/*.integration.test.ts` (no matches) + the disk-read orchestrator test name convention.

4. **[answered] are template-literal / enum-member unions in scope?**: no. `extractPrimitiveTypeFromLiteralKind.ts:15-24` maps only StringLiteral/NumericLiteral/True/False → primitive; template-literal-type unions map to `null` and throw `BadRequestError`; enum-member unions extract as references. the asset must use plain literals (as `ClaimSearch` does). out of scope, by code.

5. **[answered] is #17 the intended behavior to guard (not change)?**: yes. wisher-stated ("the fix already shipped... this task adds the test that guards it") and code-corroborated (`.why` comments declare the coercion intent). we guard, we do not alter.

6. **[research] is `extractDomainObjectMetadataForDeclarationInFile` the topmost consumer entry point, or does a higher file/program-walker wrap it?**: i did not trace the call graph above this orchestrator. not a blocker for the vision (it is verifiably *an* untested orchestrator grain), but worth a quick trace in the research phase to confirm we test the most consumer-relevant grain.

### assumptions made (explicit)
- snapshot + explicit assertions is the test style (inferred from `rule.require.snapshots` + every peer test; not wisher-stated).
- "unit/integration" in the acceptance is inclusive-or, and the orchestrator-grain half is the actionable remainder.

### research needed
- none external. one internal trace deferred — see question 6 [research].

## groundwork

### external research
none — no external dependencies. this is a pure TypeScript-AST + jest concern, all in-repo.

### internal research (verified, with citations)
- **fix is live**: `extractHomogeneousLiteralUnionType.ts` + the `allAreLiteralType` branch in `extractPrimaryTypeFromMemberDeclaration.ts:54-68` coerce homogeneous literal unions to a primitive. shipped in `00c9c64` (#17).
- **unit coverage already present**: `extractPropertiesFromInterfaceDeclaration.test.ts:202-289` (string-literal-union case + `MixedLiteralUnion` throw case). assets `ClaimSearch.ts` and `MixedLiteralUnion.ts` both introduced by `00c9c64` (#17).
- **green today**: `rhx git.repo.test --what unit --scope path://extractPropertiesFromInterfaceDeclaration --mode apply` → 9 passed, 0 failed.
- **the gap**: `extractDomainObjectMetadataForDeclarationInFile.test.ts:1-60` exercises only `Address`, `LoadingDock`, `Item` — no literal-union asset. this is the integration grain consumers actually invoke (it requires a `class` declaration via `isClassDeclaration`).
- **asset contract to reuse**: class-backed asset pattern is `interface X {...}` + `export class X extends DomainLiteral<X>|DomainEntity<X> implements X {}` (e.g. `Address.ts:1-10`). `ClaimSearch.ts` lacks the class half.
- **vocab/contract to conform to**: `DomainObjectPropertyType.{STRING,NUMBER,BOOLEAN,ARRAY,REFERENCE,DATE}`; property shape `{ type, nullable, required, of? }`; error class `BadRequestError` for mixed unions.

### contracts / vocab / stdouts to reuse
- test harness: `ts.createProgram([...]).getSourceFiles().find(...)`, then `find(isInterfaceDeclaration)` (unit) or `find(isClassDeclaration)` (integration).
- assertion style: `expect(properties.x).toMatchObject({ type, nullable, required })` + `expect(metadata).toMatchSnapshot()`.
- test runner: `rhx git.repo.test --what unit --scope path://... --mode apply` (use `--resnap` to write new snapshots).

## what is awkward?

- **the wish reads as "add the test" but the test is already present** at the unit grain. driving this literally (re-adding) would be busywork. the honest move is to surface that and steer toward the real gap (integration grain). this is the main thing to confirm with the wisher before execution.
- **`ClaimSearch` is interface-only**, so it can't be reused directly for the integration test without adding a class declaration — a small but real fork in the asset strategy that needs a decision.
- **two grains, one behavior**: there's mild redundancy between asserting literal-union coercion at the unit grain and again at the integration grain. justified (different consumers, different break surfaces), but worth naming so we don't over-build — a single focused integration case mirroring the key sub-cases is enough; we need not re-pin all seven edgecases at both grains.
