# vision: support primitive arrays as json/text column

## tl;dr — the surprising groundwork finding

> the extraction layer **already** turns `string[]` / `number[]` into a primitive-array
> shape. the real gap is **classification**, not extraction.

`extractPropertyDefinitionFromAstNode` recurses generically into array element types,
so today `tags: string[]` already extracts as:

```ts
{ name: 'tags', type: ARRAY, of: { type: STRING, nullable: false, required: true }, nullable, required }
```

proven by passing tests (see groundwork below). the pain the wisher feels lives one layer
out, in the **consumer** (`sql-dao-generator`), where the guard
`isDomainObjectArrayProperty` returns `true` for *every* array — so a `string[]` is
mistaken for an array of domain objects and rejected.

so this wish is really: **give consumers an honest way to tell a primitive array from a
domain-object array from an enum array**, plus test assets that lock in the extracted shape.

**decided with the wisher:**
- rename + narrow `isDomainObjectArrayProperty` → `isReferenceArrayProperty`, matching only
  domain-object-ref arrays (accept the public-API break for correctness + clarity).
- add `isPrimitiveArrayProperty` for `string[] | number[] | boolean[] | Date[]` (→ json/text).
- keep `enum[]` distinct (element `of.type === ENUM`) so consumers can emit native `enum[]`.
- scope is **metadata-side only** — no `sql-dao-generator` changes here.

---

## the outcome world

### day-in-the-life

a teammate models a domain object with a precise type:

```ts
export interface Provider {
  slug: string;
  tags: string[];          // ← primitive array
  ratings: number[];       // ← primitive array
  zones: ServiceZone[];    // ← domain-object array (unchanged)
}
```

they run dao codegen in the consumer. today it explodes:

```
UserInputError: According to relational database best practices, properties of persisted
domain objects should only be arrays of other domain objects ...
```

so they downgrade the model to satisfy codegen:

```ts
tags: string; // todo: revert to string[] once metadata supports primitive arrays
```

after this wish: no downgrade. `tags: string[]` and `ratings: number[]` flow through as
json/text columns. `zones: ServiceZone[]` still becomes a relation. the `// todo: revert`
comments disappear.

### before / after

| aspect | before | after |
| --- | --- | --- |
| extract `string[]` | already → `{ARRAY, of:{STRING}}` | unchanged |
| extract `number[]` | already → `{ARRAY, of:{NUMBER}}` | unchanged |
| guard for ref arrays | `isDomainObjectArrayProperty` (loose) | renamed → `isReferenceArrayProperty` (narrow) |
| `isReferenceArrayProperty(string[])` | n/a (old guard → `true`, wrong) | `false` (narrowed to ref arrays) |
| `isPrimitiveArrayProperty(string[])` | n/a (no such guard) | `true` (new guard) |
| `isPrimitiveArrayProperty(Status[])` (enum) | n/a | `false` (enum kept distinct) |
| `isReferenceArrayProperty(Item[])` | n/a (old guard → `true`) | `true` (ref arrays still match) |
| consumer codegen of `string[]` | throws `UserInputError` | json/text column (consumer task) |

### the "aha"

the value clicks when you realize the metadata was *already there* — the array's `of.type`
tells you everything. `of.type === REFERENCE` ⇒ domain-object array (relation).
`of.type ∈ {STRING, NUMBER, BOOLEAN, DATE, ENUM}` ⇒ primitive array (json/text). we just
never exposed a contract that lets a consumer branch on it cleanly.

## user experience

### who is the user?

the direct user of this repo is **another package** (`sql-dao-generator`,
`sql-schema-generator`), not a human at a terminal. the contract is the exported
type + guards.

### usecase

> "given a `DomainObjectPropertyMetadata` that is an array, tell me whether it is an array
> of primitives (→ json/text column) or an array of domain objects (→ relation), so i can
> generate the right sql."

### contract inputs & outputs

two coordinated changes (decided with the wisher):

1. **rename + narrow `isDomainObjectArrayProperty` → `isReferenceArrayProperty`** so it only
   matches arrays whose element is a domain-object reference. correctness over backcompat —
   the wisher accepts this public-API break (rename + semantic narrow, bundled into one
   release). the name now reads element-first, as the array-twin of the extant
   `isDomainObjectReferenceProperty`, so "reference array" is unambiguous. per
   `rule.require.sync-filename-opname`, the **file** moves too:
   `guard/isDomainObjectArrayProperty.ts` → `guard/isReferenceArrayProperty.ts` (with its
   `.test.ts`), and the `src/index.ts` export updates.

```ts
// old: isDomainObjectArrayProperty — true for EVERY array (ambiguous name, loose body)
// new: isReferenceArrayProperty    — true only when element is a domain-object reference
isReferenceArrayProperty(property): property is DomainObjectPropertyMetadata & {
  of: DomainObjectReferenceMetadata;
} => property.type === ARRAY && isDomainObjectReferenceProperty(property.of);
```

> note on "reference": in this repo, `isDomainObjectReferenceProperty` already treats
> "reference" as `of.type === REFERENCE` — which covers **both** nested domain objects
> (`Item[]`) and by-uuid refs (`Ref<typeof Item>[]`); extraction collapses both to
> `REFERENCE` (`extractPropertyDefinitionFromAstNode.ts:145-171`). `isReferenceArrayProperty`
> inherits that same broad sense as its array-twin — it is NOT limited to by-uuid refs.

2. **add `isPrimitiveArrayProperty`**, exported alongside the peers:

```ts
import { isPrimitiveArrayProperty } from 'domain-objects-metadata';

isPrimitiveArrayProperty(property): property is DomainObjectPropertyMetadata & {
  of: Omit<DomainObjectPropertyMetadata, 'name'>;
};
```

returns `true` when `property.type === ARRAY` **and** the element `of.type` is a primitive
(`STRING | NUMBER | BOOLEAN | DATE`). returns `false` for domain-object arrays
(`of.type === REFERENCE`) **and** for enum arrays (`of.type === ENUM`, kept distinct — see
below).

> **enum arrays are kept distinct.** an `enum[]` is *not* lumped into the primitive/json
> bucket. it stays classifiable as an enum array so a consumer can emit a native postgres
> `enum[]` column rather than json/text. (whether to expose a third guard like
> `isEnumArrayProperty` or have consumers branch on `property.of.type === ENUM` is a design
> detail for the next stone; the metadata already carries `of.type === ENUM`.)

### what it looks like to leverage (consumer-side, illustrative — NOT built in this task)

```ts
// consumer would branch on three array kinds:
if (isReferenceArrayProperty(property)) { /* relation / foreign keys */ }
if (property.of.type === ENUM)          { /* native enum[] column */ }
if (isPrimitiveArrayProperty(property)) { /* json/text column */ }
```

scope note: the consumer (`sql-dao-generator`) change is **out of scope** for this task.
this repo delivers the metadata-side classification + test assets only.

### timeline

1. extract (already works) → `{ ARRAY, of: { STRING } }`
2. hydrate (already works) → primitive element passes through untouched
3. classify (new) → `isPrimitiveArrayProperty` ⇒ `true`
4. consumer maps to json/text column (separate downstream task)

## mental model

- to a friend: *"arrays of plain values like `string[]` now get stored as one json column
  instead of being mistaken for a table of linked records."*
- analogy: a `string[]` is a **bag of values you carry inside the row** (json/text); a
  `Provider[]` is a **set of links to other rows** (foreign keys / join). the metadata
  already knew which was which; we just hand the consumer a labelled handle.

| they say (consumer dev) | we say (this repo) |
| --- | --- |
| "json column" / "text column" | primitive-array property (`of.type` is primitive) |
| "linked records" / "join" | domain-object-array property (`of.type === REFERENCE`) |

## evaluation

### how well does it solve the goal

- directly unblocks issue #24 acceptance: test assets for `string[]` + `number[]`,
  extracted primitive-array shape with nullable/required preserved, ref-array behavior
  intact under the renamed guard.
- no change to the extracted/hydrated metadata shape — only the guard surface changes.

### pros

- the extracted shape is already correct and snapshot-locked; we mostly *prove* and
  *label* it.
- `isReferenceArrayProperty` reads element-first and pairs with the extant
  `isDomainObjectReferenceProperty`, so its meaning is unambiguous and it reuses that guard
  to classify the element.
- guards are mutually exclusive → order-independent for consumers (no footgun).

### cons / tradeoffs

- **`isDomainObjectArrayProperty` is renamed + narrowed → `isReferenceArrayProperty`.** two
  public-API breaks in one release (the export name changes AND the semantics narrow),
  accepted by the wisher; any extant consumer that imported the old name or relied on it
  matching `string[]` must update. mitigated by tests + a clear changelog note.
- the actual json/text column emission is a **consumer** change (separate, out-of-scope
  task per the wisher); this wish only supplies the metadata-side handle.

### edgecases & pit-of-success

| edgecase | behavior |
| --- | --- |
| `string[] \| null` (nullable array) | `nullable: true` preserved on outer; element stays `required:true, nullable:false` |
| `tags?: string[]` (optional) | `required: false` preserved |
| `(string \| null)[]` | element union handled by the extant union branch → element STRING |
| `Variant[]` where `type Variant = 'A'\|'B'` | element hydrates to STRING ⇒ primitive array (json/text) |
| `Status[]` where `Status` is an enum | element `of.type === ENUM` ⇒ **enum array, kept distinct** (native `enum[]`, not json/text) |
| `Item[]` (domain object) | element `of.type === REFERENCE` ⇒ `isReferenceArrayProperty` ⇒ relation (unchanged) |
| `Ref<typeof Item>[]` (by-uuid ref) | also `of.type === REFERENCE` ⇒ `isReferenceArrayProperty` (same as nested; extraction collapses both) |

> ⚠️ **correction (post-execution):** the two `→ STRING` rows above (`(string \| null)[]`,
> `Variant[]`) proved **inaccurate** — `(string \| null)[]` throws at extraction and
> `Variant[]` throws at hydration; neither degrades to STRING. the accurate behavior lives
> in the "discovered vision inaccuracies" section of `5.1.execution.from_vision.yield.md`
> and is locked in by throw-regression tests in `introspect.test.ts`.

## open questions & assumptions

### assumptions

1. **scope is metadata-only.** **confirmed by wisher** — no `sql-dao-generator` changes in
   this task. this wish delivers the metadata-side classification + test assets only.
2. **shape stays the same.** primitive arrays keep the extant `{ ARRAY, of: {...} }`
   shape rather than a new `DomainObjectPropertyType` variant, so the snapshot holds.
   (note: the *guard surface* changes — rename + narrow, see decision 1 — but the
   extracted/hydrated metadata shape does not.)
3. **enum arrays are kept distinct** from primitive arrays — **confirmed by wisher**. an
   `enum[]` is classifiable as an enum array (element `of.type === ENUM`), not collapsed
   into the json/text primitive bucket, so a consumer can emit a native `enum[]` column.

### open questions (all resolved)

1. **[decided] tighten `isDomainObjectArrayProperty`.** wisher chose **rename + narrow** →
   `isReferenceArrayProperty`, matching only arrays whose element is a domain-object
   reference — correctness over backcompat; the public-API break is accepted. `string[]`
   and `enum[]` return `false` from this guard.
2. **[decided] scope = metadata-side only.** wisher confirmed **no** `sql-dao-generator`
   changes in this repo/task. consumer codegen is a separate downstream effort.
3. **[decided] guard names.** the new primitive guard is `isPrimitiveArrayProperty` (mirrors
   the `DomainObjectPropertyType` primitives vocabulary). the renamed ref guard is
   `isReferenceArrayProperty` — element-first, the array-twin of the extant
   `isDomainObjectReferenceProperty`, chosen over the ambiguous `isDomainObjectArrayProperty`
   (which could parse as "an array property on a domain object").
4. **[answered] hydration precondition.** `isPrimitiveArrayProperty` (and
   `isReferenceArrayProperty`) are only correct on *hydrated* metadata. via code:
   `getHydratedDomainObjectMetadatasFromFiles.ts:74-83` turns an inner enum REFERENCE into
   ENUM only at hydration; pre-hydration an enum array element is still REFERENCE,
   indistinguishable from a domain-object array. ⇒ the guards must document "operates on
   hydrated metadata"; `introspect` already returns hydrated metadata.
5. **[decided] enum-array column type.** wisher chose **kept distinct** — `enum[]` stays an
   enum array (element `of.type === ENUM`) so a consumer can emit a native `enum[]` column,
   NOT json/text. `isPrimitiveArrayProperty` therefore excludes ENUM elements.

## what is awkward?

- **the wish's premise is slightly off.** it says "today only arrays of domain objects are
  supported." at the *extraction* layer that's false — primitive arrays already extract.
  the friction is at the *consumer classification* layer. the vision corrects this so we
  don't build a redundant "extraction" fix that already ships.
- **the loose, ambiguously-named guard — now resolved.** `isDomainObjectArrayProperty` had
  two problems: (a) its body returned `true` for *every* array (loose), and (b) its name is
  ambiguous — it could parse as "an array property *on* a domain object" (vacuous — every
  property is) or "a property that *is* an array of domain objects" (the useful sense). the
  wisher chose the clean fix: **rename + narrow → `isReferenceArrayProperty`**, matching only
  domain-object-ref arrays. element-first, it pairs with the extant
  `isDomainObjectReferenceProperty`, so "reference array" is unambiguous. this removes the
  order-dependent-correctness footgun entirely — each guard now means exactly what its name
  says.
- **enum arrays sit in a third bucket.** not a domain-object array, not a primitive array —
  an enum array. the wisher chose to keep it distinct so consumers can emit native `enum[]`.
  the slight awkwardness: a consumer now branches on three array kinds, not two. acceptable
  for the column-type precision it buys.
- **split deliverable.** the user-visible payoff (no more codegen rejection) only lands
  after a *separate* consumer change — confirmed out of scope by the wisher. this task
  delivers the metadata-side classification; expectations are set accordingly.
